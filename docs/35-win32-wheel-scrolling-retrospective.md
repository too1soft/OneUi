# OneUI Win32 鼠标滚动与帧调度复盘

日期：2026-08-03

## 1. 背景与结论

iShellPro 原生主机列表曾连续出现四类滚动问题：

- 列表绘制掉帧，滚动时肉眼可见不流畅；
- 优化绘制后，滚动变得滞后、不跟手；
- 一次物理滚轮动作被表现为先小幅、再大幅的两段滚动；
- 某些修改会导致 UI 线程繁忙、窗口卡死，或者把滚动速度降得过慢。

最终确认这不是某个业务页面的特殊问题，而是 OneUI 的 Win32 帧调度、滚轮输入合并和滚动运动模型需要统一治理。最终实现遵循以下原则：

1. 一个物理手势只有一个连续运动状态；后续滚轮数据包只更新目标，不重启动画。
2. 运动位置由时间解析求解，不依赖帧数，因此不会把 200 Hz 的参数写死到产品中。
3. Win32 消息与动画帧在同一个可等待消息泵中公平调度，动画不能通过自投消息占满 UI 线程。
4. 窗口按当前所在显示器读取刷新率，支持 60/75/120/144/165/200 Hz 等常见模式，并在切换显示器后重新检测。
5. 性能和手感问题必须由输入、运动、帧间隔和绘制耗时 trace 共同判断，禁止继续凭感觉堆补丁。

## 2. 根因分析

### 2.1 动画消息形成 UI 线程忙循环

旧实现通过立即投递新的动画消息来驱动下一帧，并在 UI 线程调用 `DwmFlush()`。在当前栅格渲染路径中，`DwmFlush()` 没有形成可靠的逐帧节拍，实际 trace 可观察到约 5 ms 一次的忙循环。结果是：

- 动画消息可能持续挤占普通窗口消息；
- 输入、绘制和动画回调互相干扰；
- 高负载时会出现卡死或长时间无响应；
- 帧率由消息处理速度偶然决定，而不是由显示器刷新率决定。

### 2.2 把滚轮数据包当作彼此独立的动画

高分辨率或带加速的鼠标，一次物理滚动会产生多个间隔不规则的 `WM_MOUSEWHEEL` 数据包。实测样本中，第一包为 `-120`，约 258 ms 后出现加速后的 `-720`。

如果每个数据包都启动一段新动画，用户会感到“一次滚轮滚了两次”；如果第一段过早结束，第二包到达时也会重新产生一次明显的启动冲击。

### 2.3 固定刷新率判断错误

仅使用 DWM composition timing 在测试机器上得到 60 Hz，但显示器实际工作在 200 Hz。这样即使运动曲线正确，窗口也只按约 16.7 ms 采样一次，用户仍会看到明显的低帧率。

刷新率属于窗口当前显示器，而不是整个应用的常量。窗口跨显示器移动时也必须重新解析。

### 2.4 直接缩短整段动画会破坏手势连续性

将所有滚动统一压缩到约 110 ms，虽然单段更快，但第一包会在第二个设备包到达前完全停止，从而再次暴露两段式滚动。滚动速度和数据包合并不能由一个固定时长同时解决。

## 3. 最终架构

### 3.1 单一解析运动状态

`SmoothScrollMotion` 保存以下状态：

- 当前值 `value`；
- 目标值 `target`；
- 当前速度 `velocity`；
- 可滚动上下界；
- 上一次采样时间；
- 临界阻尼角频率。

运动采用临界阻尼解析解。每一帧直接根据真实经过时间计算位置和速度，不进行“每帧加固定像素”的积分。因此同一段滚动在 60 Hz 和 200 Hz 下具有相同的距离、时长和停止位置，仅可见中间帧数量不同。

同方向后续输入执行 retarget：

- 保留当前速度；
- 将新增距离追加到当前目标；
- 不重复注入第二次冲量；
- 不创建第二个动画对象。

反方向输入执行 direction reset：

- 丢弃尚未完成的同向排队距离；
- 从当前可见位置建立反方向目标；
- 重置与新方向冲突的速度。

### 3.2 首包与重定向分离调参

公开参数位于 `ScrollMotionSpec`：

| 参数 | 当前值 | 含义 |
| --- | ---: | --- |
| `initialSettlingDurationMs` | 150 ms | 首个输入包的近似稳定时间，用于覆盖设备数据包间隔并维持手势连续性 |
| `retargetSettlingDurationMs` | 110 ms | 运动中追加目标后的近似稳定时间，决定连续滚动的跟手速度 |
| `inputVelocityRatio` | 0.55 | 新运动或反向运动的初始速度比例 |
| `maximumVelocityRatio` | 0.90 | 按剩余距离约束的最大速度比例 |

这两个时长必须分开维护：首包负责“不断”，重定向负责“够快”。当前值来自真实输入日志与用户手感确认，不是页面级魔法数字。

### 3.3 Win32 帧调度

Win32 backend 使用高分辨率 waitable timer，并在不支持时回退到普通 waitable timer。消息泵通过 `MsgWaitForMultipleObjectsEx` 同时等待：

- 动画帧定时器；
- Win32 输入与窗口消息。

每轮优先排空已有窗口消息，再执行到期动画帧。`requestAnimationFrame` 在任意时刻只保留一个待执行帧，避免重复排队。该路径不再依赖 `DwmFlush()`，也不通过递归投递消息制造忙循环。

### 3.4 每显示器刷新率解析

帧间隔按窗口当前 `HMONITOR` 缓存：

1. `MonitorFromWindow` 获取窗口所在显示器；
2. `GetMonitorInfoW` 获取显示设备名；
3. `EnumDisplaySettingsW(..., ENUM_CURRENT_SETTINGS, ...)` 读取当前刷新率；
4. 读取失败时回退到 DWM composition timing；
5. 仍失败时使用 60 Hz 安全默认值。

窗口移动到另一块显示器时，`HMONITOR` 变化会触发重新读取；收到 `WM_DISPLAYCHANGE` 时主动清除缓存。实现不假设用户使用 200 Hz 显示器。

## 4. 诊断设施

滚动 trace 默认完全关闭，不影响正式运行。需要诊断时设置：

```powershell
$env:ONEUI_SCROLL_TRACE = "$env:TEMP\oneui-scroll.csv"
```

CSV 会记录：

- Win32 收到和分发的滚轮输入；
- 输入 delta 与相邻数据包时间；
- 当前 offset、target 和 velocity；
- 每个动画帧的真实间隔；
- 每帧位移；
- 绘制耗时；
- 动画开始、重定向和停止状态。

复现时必须保留完整的一次物理滚轮动作，不能只截取最终 offset。重点判断：

1. 一个物理动作产生了多少个系统数据包；
2. 是否只有一个连续运动状态；
3. target 是否只追加一次输入距离；
4. 速度在同方向 retarget 时是否连续；
5. 帧间隔是否接近当前显示器刷新周期；
6. paint 是否占满一个刷新周期；
7. UI 消息响应是否在动画期间恶化。

## 5. 验证结果

测试机器当前显示器为 200 Hz。修复后的真实输入样本为 `-120`，间隔约 258 ms 后追加 `-720`。

| 指标 | 结果 |
| --- | ---: |
| 解析到的显示器刷新率 | 200 Hz |
| 平均动画帧间隔 | 约 5.88 ms |
| 完整运动时间（含 258 ms 设备包间隔） | 约 558.5 ms |
| 上一版完整运动时间 | 约 639.7 ms |
| 最终滚动位置 | 378 px |
| 最终速度 | 0 |
| 窗口响应状态 | 正常 |

压力测试期间：

- 80 次响应探测平均约 0.81 ms；
- p95 约 1.53 ms；
- 最大约 5.38 ms；
- CPU、句柄与内存没有持续增长。

自动化验证：

- OneUI C++ / CTest：12 项通过；
- OneUI Rust bindings：23 项通过；
- iShellPro native shell：50 项通过。

## 6. 后续调手感的标准流程

### 6.1 允许调整的参数

优先只调整 `ScrollMotionSpec`，不要修改 Win32 消息泵或给某个业务页面增加滚动分支。

- 觉得连续滚动太慢：小幅降低 `retargetSettlingDurationMs`。
- 觉得首包启动迟缓：小幅提高 `inputVelocityRatio`，同时检查是否出现过冲。
- 觉得高速滚轮冲得太猛：降低 `maximumVelocityRatio`。
- 觉得一次物理动作重新分段：优先检查真实包间隔，不要盲目降低 `initialSettlingDurationMs`。

每次只改一个维度，建议单次变化不超过 10% 到 15%。

### 6.2 必测矩阵

每次手感调整至少覆盖：

- 60 Hz、120/144 Hz、200 Hz 或可用的最高刷新率；
- 普通滚轮单格、连续快速滚轮、高分辨率滚轮/触控板；
- 同方向连续输入、立即反向、滚动到顶部和底部；
- 短列表、长虚拟列表、绘制负载较高的列表；
- 窗口跨不同刷新率显示器移动；
- 动画期间的点击、hover、键盘和窗口拖动响应。

### 6.3 禁止做法

- 禁止按显示器帧数累加固定像素；
- 禁止把 200 Hz 或其他刷新率写成应用常量；
- 禁止为 iShellPro 主机列表增加 OneUI 之外的滚动补偿；
- 禁止同时保留系统滚动和自定义滚动两条路径；
- 禁止每个滚轮包重新启动独立缓动；
- 禁止在 UI 线程使用等待呈现的阻塞调用控制节拍；
- 禁止没有 trace 和回归数据就宣布性能问题已经解决。

## 7. 维护边界

OneUI 负责：

- 原始输入时间戳；
- 手势数据包合并；
- 滚动运动模型；
- 刷新率感知和帧调度；
- ScrollView/VirtualList 的滚动一致性；
- 通用 trace 与行为测试。

下游产品负责：

- 设置合理的每格滚动距离；
- 提供正确的内容高度和虚拟列表数据；
- 避免在滚动回调中执行阻塞业务工作；
- 通过公开 OneUI API 使用滚动，不复制框架内部实现。

这条边界保证后续 Remote、WYC、iShellPro 等产品共享同一套滚动行为，不再由每个页面分别修复。
