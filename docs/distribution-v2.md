# OneUpdate 兼容分发契约（P3 实施设计，尚未启用）

本文件是明确的接入设计，不代表服务端、Agent 或 Catalog 已完成修改。
可执行筛选规范为 distribution.py，反例测试在 tests/test_distribution.py。

## 请求与签名隔离

- 保持旧 UpdatePlan JSON 字段、序列化规则及历史签名不变。
- 新请求能力标识固定为 `windows_compat_v2`，增加 client_type、installed_profile、installed_build_id、native_arch。
- 现有 arch 表示已安装产品架构，不能再由 Agent 自身位数推断；os_version 使用实际 RtlGetVersion。
- 仅能力协商通过后返回 plan_version=2；新计划增加签名内的 compatibility 对象，包含产品、客户端类型、profile、architecture、build_id、最低系统、验收系统、最低底座版本及健康协议版本。
- 签名必须覆盖整个 v2 对象；不能先验旧对象后相信一个未签名 compatibility 旁路字段。
- 上传、Worker、Catalog、安装器、Agent 均传递同一个构建 manifest，必须验证内容哈希，不能靠文件名或管理员标签认定 Win7。
- 跨语言规范化 JSON 和签名 fixture 必须先通过 Go/Rust 双向验证；本轮 Python 构建 ID 规范不自动等于已有 Go/Rust 签名规范。

## 候选筛选顺序

1. 校验产品、客户端、系统版本、原生架构、已安装架构及 profile；未知则停止。
2. 过滤同应用、客户端类型、通道、profile、架构、最低系统、真实验收系统、已发布状态。
3. 在兼容集合中取最新产品版本，再执行该版本灰度。
4. 没有兼容版本，保留现程序；不能先取最新再失败，也不能把旧包一律视为兼容。
5. 同版本同组合出现不同构建身份，拒绝发布 / 激活，不以 sequence 掩盖版本重复。

本地在验签、完整文件校验、有效期检查之后，重复执行 OS/架构/profile 检查。健康确认精确匹配 build ID。
profile 与架构迁移必须由明确的修复 / 迁移安装器处理，不能由普通更新完成。

## 数据库追加迁移

必须单独部署 OneUpdate 数据库迁移；不修改 WYC 业务数据库。
当前发布键为应用 + 通道 + 版本 + 架构。新键需要再包含客户端类型及 profile。
历史记录新增状态为 unknown/unverified，旧的 min_os_version=6.1.7601 不得作为证据。

迁移前只读导出：发布 ID、当前键、版本、sequence、制品 SHA256、旧最低系统、现存元数据和引用它的安装 / 下载任务。
先解决唯一键冲突，再通过追加迁移引入新键、构建身份与验证状态；不得修改历史签名内容。
本轮未创建或执行此迁移，避免让未完成的新协议进入既有发布链路。

## 旧安装与底座升级

旧 Agent 不理解 profile/build ID，必须走经过验证的 bridge；无法验证其当前身份时提供一次人工修复安装器。
修复安装器保持应用隔离，核对原目录、架构、配置版本和签名，不导入其他应用的状态。

底座升级事务设计：

```text
校验候选底座与权限 → 持久化维护任务 → 独立维护进程接管
→ 停止指定应用 Agent → 备份 → 原子替换 → 启动 → 精确健康确认
→ 成功归档；失败恢复旧底座并恢复原应用状态
```

不得覆盖运行中的 Agent；不得继续“文件存在就跳过更新”。断电恢复通过持久化任务的阶段判断，重复执行保持幂等。
安装器、启动器、卸载器和 FFI 全链路仍需验证；不能因为 agent --help 可运行而认定更新闭环通过。

## 下载

首次安装：Win10/11 默认 modern；Win7 SP1、Win8/8.1 默认 legacy；64 位 OS 优先 x64。
通用在线引导只负责识别并交接同架构正式安装器，不承担跨架构安装。
已有 legacy 程序在 OS 升级之后仍沿原组合更新。
缺数据、识别失败、验收系统不匹配都显示明确失败 / 手动入口，不猜测。
网站继续以 Catalog 为唯一版本 / 下载地址来源，不增加第二张手工版本表。
